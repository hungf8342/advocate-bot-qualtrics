advocate-bot-qualtrics

A legal-intake chatbot that walks a self-represented defendant through a fixed decision tree about a debt-collection complaint, using an LLM only to classify each answer — not to make legal decisions. This page traces exactly how a message becomes a response.

Anthropic tool-use deterministic host SOL → FDCPA Excel export

1. Overview

The service has two phases. First, a one-time extraction reads a complaint PDF and produces a structured ComplaintFactSheet JSON (parties, amounts, filing date, last-payment date, causes of action). That step is separate and uses its own prompt/model.

Second — the focus of this page — is the interactive decision tree. After facts are extracted, a stateful host engine drives a fixed sequence of yes/no and date questions to assess two possible affirmative defenses:

Statute of Limitations (SOL)

Is the gap between the complaint's filing date and the most recent payment greater than the (demo) 3-year limit? Computed by the host, never the LLM.

FDCPA conduct

Did the debt collector threaten arrest, disclose the debt to third parties, and is there evidence? Also a pure host computation from collected flags.
Key design principle. The LLM is a classifier, not a decision-maker. Its only job per turn is to read the user's free-text reply and pick which branch of the current node it matches (plus a confidence score). All routing, legal computation, date parsing, and state live in deterministic Python (the "host"). The system prompt (prompts/decision_tree_chat_system.md) explicitly forbids the model from doing any defense analysis.

3. The decision tree

The tree is a plain Python dict of nodes plus separate routing tables — it is data, not code paths. It lives entirely in decision_tree/interactive_tree.py.

3a. Node anatomy

Every node is a CurrentNode (schemas.py) with an id, a question, and a list of TreeBranch options. A branch's branch_id is the value the LLM must return as next_node_id. Two nodes are hook nodes with no branches — they are pure host computations.

# interactive_tree.py — a representative node
"confirm_filing_date": CurrentNode(
    node_id="confirm_filing_date",
    question=f"Is the filing date of the complaint {date_complaint_filed}?",
    branches=[
        TreeBranch(branch_id="yes", label="Yes, that is the filing date."),
        TreeBranch(branch_id="no",  label="No, that is not the filing date ..."),
    ],
),
# a hook node — branches=[], host runs the math:
"sol_computation": CurrentNode(node_id="sol_computation", question="Computing statute of limitations: ...", branches=[]),

The question string can contain the tokens {date_complaint_filed} and {date_user_failed_to_pay}. render_interactive_node() replaces these with the live session value (falling back to the fact sheet, or the literal "unknown") before the node is ever shown to the user or sent to the LLM.

3b. Routing & hooks

The LLM never decides where to go next. It only returns a branch_id. The host maps (current_node_id, branch_id) → next_node_id via three structures:

StructurePurpose
INTERACTIVE_ROUTESStatic (node, branch) → next node table for ordinary branching.
resolve_interactive_next_node()Wraps the table. For contact_third_parties it routes conditionally on session flags: if neither threatened nor disclosed, it skips the evidence question and jumps straight to fdcpa_computation.
INTERACTIVE_HOOK_ADVANCESWhere a hook node goes after it computes: sol_computation → threatening_arrest, fdcpa_computation → review_questions.

When the host lands on a hook node it does not call the LLM. Instead _drain_hooks() loops: run the computation (run_sol_computation / run_fdcpa_computation), emit a result message, then advance_from_hook() to the next node — repeating if the next node is also a hook.

How the SOL and FDCPA computations actually decide (interactive_computations.py) 
# SOL_LIMIT_DAYS = 1095  (demo ≈ 3 × 365; NOT calendar-year legal analysis)
def run_sol_computation(session):
    last_payment = max(complaint, og_creditor, debt_collector dates present)
    if (filing_date - last_payment).days > 1095:
        return "SOL is an affirmative defense."
    return "SOL is not an affirmative defense."

def run_fdcpa_computation(session):
    conduct = session.threatened or session.disclosed
    if conduct and session.evidence: return "FDCPA violation is an affirmative defense."
    if conduct:                  return "FDCPA violation is a potential affirmative defense."
    return "FDCPA violation is not an affirmative defense."

5. Behind the scenes, step by step

This traces a single ordinary turn — the user answering a branching node — from InteractiveChatEngine.submit() to the returned assistant message(s). File and function references are exact.

  1. Append the user turn host
    submit() strips the message, rejects empties, and appends ("user", text) to self.transcript. interactive_host.py
  2. Hook / terminal short-circuit host
    If the current node is a hook (is_interactive_hook_node) it drains hooks and returns — no LLM. If it is review_questions it routes to terminal Q&A (_submit_terminal_qa). Otherwise it proceeds to _submit_tree_node().
  3. Render the node host
    render_interactive_node(node_id, facts, session) substitutes the date tokens with the live session value (or fact-sheet fallback, or "unknown") in both the question and branch labels.
  4. Pure-IDK skip check (no LLM) host
    is_pure_idk(user_message) (confidence.py) matches phrases like "I don't know" without any yes/no lean. If matched and the node has a configured INTERACTIVE_IDK_SKIP_BRANCH, the host advances on that default branch with confidence=0, skipped=True, emits "No problem — we'll move on", and never calls the model. A hedged answer ("I think yes") does have a lean, so it falls through to the LLM.
  5. Build the LLM payload host
    build_user_payload(transcript, user_message) assembles up to the last MAX_TRANSCRIPT_TURNS = 8 turns into a text block ending with "Latest user message:\nUser: …".
  6. process_chat() assembles the request host
    process_chat.py loads the system prompt, then builds a payload dict containing the rendered current_node, the complaint_fact_sheet (with field_citations excluded), the raw user_message transcript, the full confidence_scoring_calibration text, and the confidence_hedge_threshold.
  7. Single Anthropic call, forced tool-use LLM
    submit_chat_turn() (chat_structured.py) calls claude-haiku-4-5 at temperature=0.0 with one tool (submit_chat_turn, schema = ChatTurnResponse.model_json_schema()) and tool_choice={"type":"tool"} — forcing structured output. The tool_use block is validated into a ChatTurnResponse. The whole payload dict is stringified into the user message.
  8. Post-validate the classification host
    _post_validate_turn() enforces invariants the model could violate: non-answer_node intents get next_node_id/confidence nulled; answer_node with a missing, empty, or out-of-tree next_node_id raises ChatError; a missing confidence raises; and clamp_answer_confidence caps it at 70 if the latest message contains "think/maybe/not sure".
  9. Branch vs. non-branch outcome host
    If intent ≠ answer_node (e.g. ask_about_complaint, off_topic, unclear), the host simply returns turn.assistant_reply and stays on the same node. Otherwise it continues to apply the branch.
  10. Date extraction (when relevant) host
    parse_submitted_date(user_message) regex-scans for ISO, slash, and month-name dates and keeps the latest. On a submit branch with no parseable date, the host replies with a clarification and does not advance.
  11. Apply branch + record answer host
    _advance_on_branch() calls apply_interactive_branch() (stores collected dates, sets filing_date_changed/last_payment_date_changed on disputes, sets FDCPA flags threatened/disclosed/evidence on "yes") and record_node_answer() (stores branch_id + confidence + skipped into session.node_answers[node_id]).
  12. Hedge message (low confidence) host
    If confidence_pct < CONFIDENCE_HEDGE_THRESHOLD (default 70), resolve_confidence_hedge_message() takes the LLM's first sentence if it is a valid hedge (≥10 chars, not a question, not the next tree question, and the original wasn't multi-sentence) else a generic fallback. This is prepended to the outgoing messages.
  13. Resolve the next node host
    resolve_interactive_next_node(node_id, branch_id, session) looks up INTERACTIVE_ROUTES (with the conditional override for contact_third_parties). _skip_date_node_if_collected() skips a date node whose value was already captured (e.g. an additional-payment date supplied inline).
  14. Drain hooks & emit next question host
    If the new node is a hook, _drain_hooks() runs SOL/FDCPA in pure Python, appends a "Result: …" message, and advances. Landing on review_questions calls _set_tree_complete(). Otherwise the host appends the next node's rendered question. All assistant messages produced this turn are returned in InteractiveChatStep.assistant_messages.
  15. Completion & export host
    _set_tree_complete() → _maybe_export_session_fields() appends one wide row to session_fields.xlsx (once). After completion, further user messages go to the terminal Q&A handler, which forbids the answer_node intent.
Exact Anthropic call (chat_structured.py) 
def submit_chat_turn(*, system, payload):
    client = AnthropicClient()
    user_text = payload if isinstance(payload, str) else str(payload)
    response = client.complete(
        model=get_anthropic_chat_model(),          # claude-haiku-4-5-20251001
        system=system,                             # decision_tree_chat_system.md
        messages=[{"role": "user", "content": user_text}],
        temperature=0.0,
        tools=[_chat_turn_tool()],                 # input_schema = ChatTurnResponse
        tool_choice={"type": "tool", "name": CHAT_TOOL_NAME},
    )
    tool_input = _parse_anthropic_tool_use(response)
    return ChatTurnResponse.model_validate(tool_input)

6. Confidence & hedges

Confidence is a per-node 0–100 score the LLM assigns to the branch it chose, guided by the calibration index in prompts/confidence_scoring_calibration.md:

BandMeaningExample user reply
90–100High certainty / definitive"Yes, I am positive."
70–89Moderate; mostly sure, no hard proof"I'm pretty sure," "I believe so."
50–69Tentative / hedged"I think," "Maybe," "let's say yes."
0–49No meaningful lean → host skips (no answer_node)"I don't know."

Two host-side guardrails sit on top of the LLM's number:

  • Hard clamp. clamp_answer_confidence() forces the score to ≤ 70 whenever the latest message contains "think", "maybe", or "not sure" — matching the calibration's CRITICAL rule, regardless of what the model returned.
  • Hedge surfacing. When the final score is below CONFIDENCE_HEDGE_THRESHOLD (default 70, env-overridable), the host emits a single hedge sentence before moving on. The LLM is instructed to write exactly one acknowledging sentence in assistant_reply when below threshold; resolve_confidence_hedge_message() validates/sanitizes it (first sentence only, no question, not the next tree question) and falls back to "You seemed unsure about that — we'll move forward with what you indicated."
Pure-IDK vs hedge. A pure "I don't know" (no lean) is caught by is_pure_idk() before the LLM call and skips the question with a default branch and confidence 0. A hedged answer with a lean ("I think yes") still calls the LLM, routes on the leaned branch, and produces a hedge message.

7. Sessions & Excel export

All conversation state lives in InteractiveSessionState (interactive_session.py): the four collectible dates, the filing_date_changed/last_payment_date_changed correction flags, the three FDCPA booleans, and a node_answers dict of NodeAnswerRecord(branch_id, confidence_pct, skipped). The session is seeded from the fact sheet by init_session_from_fact_sheet() (filing date and last-payment complaint date).

When the tree completes (reaching review_questions), append_session_fields_row() (session_field_export.py) writes one wide row per conversation to output/session_fields.xlsx (override via SESSION_FIELDS_XLSX_PATH). For each of the four date fields it _pick_source_node()s the confidence from the first matching answered node, and — when a date was user-corrected — caps that field's confidence at CORRECTION_CONFIDENCE_CAP = 69 (strictly below 70).

9. Notes & caveats

  • Scaffolding status. The README marks the tree definitions as placeholders not yet validated for legal correctness. The SOL threshold (SOL_LIMIT_DAYS = 1095) is a demo approximation of "3 years", not real calendar-year analysis.
  • Assistant wording in the examples is illustrative. Branch choices, routing, flags, dates, and computation results above are exact to the code, but the natural-language fact answers and hedge sentences are generated by the LLM at runtime, so their exact phrasing will vary.
  • Models. The interactive chat uses claude-haiku-4-5-20251001 (DEFAULT_ANTHROPIC_CHAT_MODEL), distinct from the extraction default claude-sonnet-4-6. Both are env-overridable.
  • Judgment call — "off_topic"/"unclear" routing. The code keeps the user on the same node and returns the model's reply for any non-answer_node intent (_submit_tree_node returns without advancing). I represented this in Example 4b with the ask_about_complaint turn; the same path applies to off_topic/unclear.
  • Judgment call — embedded dispute dates. _consume_embedded_dispute_date() lets a user supply a corrected date inline on a confirm/dispute node, applying it and skipping the dedicated get_* node. The examples use the explicit multi-step path for clarity, but this shortcut exists in the engine.
